> production code yet. File and line references describe the tree at `385b6f9`
> (branch `feat/ui-review`) and are kept as history once CR6 is implemented.

> Dated 2026-11-11.

## 1. Reference description of the new model

Every document that describes the city reuses these sentences, so all of them
say the same thing.

- **Plan from a seed.** Each focus session has a *city plan*: roads, lots,
  buildings with their floors, colors, props and tower names. The plan is
  generated by a pure function from a seed derived from the session id, so it is
  different every session and identical every time the same session is redrawn.
  Geometry is never stored.
- **Floors from progress.** The visible city is derived from the plan and the
  session's `builtCharacters`. More characters show more floors, in a fixed
  build order; fewer show fewer, newest floors first.
- **Malus through the score.** Time on a blocked site costs characters with an
  escalating schedule *inside* `builtCharacters`, so the score, the tiers, the
  population and the city all lose the same amount. A partly paid top floor is
  drawn damaged, so a single lost character is visible.
- **3D view with an ASCII fallback.** The City tab draws the plan with three.js,
  loaded only when the tab opens. Without WebGL2, or after a lost context, it
  shows an ASCII skyline derived from the same plan.
- **Fixed environment, session palettes.** Black floor, phosphor-green grid,
  rain and HUD text are always the same (`#7dfba0`, DESIGN.md). Only the
  buildings change: a neon palette per session plus a small hue shift.

Facts that shape the decisions:

- **The drawing and the score disagree today.** The score subtracts distraction
  linearly (1 character per tick); the drawing loses `1 + malusForDistractionTicks(n)`.
  30-minute session (`tickMs` 3 000 ms), 60 s on a blocked site: the score loses
  20 characters, the drawing 45.
- **`city.buildings`, `selectCityBuildings` and per-domain colors are unused.**
  CR6 does not revive them (YAGNI): tower names are generated, colors come from
  the session palette, not from blocklist domains. The sketch's "site colored
  edges" were a visual idea, not a requirement.
- **`MALUS_APPLIED` has no UI consumer.** Its payload can change freely if the
  bus tests keep passing.
- **`GROWTH_TICK_MS` (2 000 ms)** in `growth-engine.ts` is a legacy constant; the
  real cadence is `FocusPreset.tickMs = duration / 600`.

## 3. The `CityPlan`

All in `lib/city/plan/` (pure, no DOM, no three.js). Types in
`lib/city/plan/city-plan.types.ts` (CR6.T2a built `GroundPlan` = seed, layout id, offset, bounds, roads, lots; CR6.T2b extends it to the `CityPlan` below; CR6.T3 adds `paletteId`, `hueShift` and the building colors). Sections and floors are as built; see "Buildings as built".

```ts
interface CityPlan {
  readonly seed: number;
  readonly layoutId: string;
  readonly paletteId: string;
  readonly hueShift: number;             // degrees, integer
  readonly bounds: { width: number; depth: number };   // ground cells
  readonly roads: ReadonlyArray<RoadSegment>;
  readonly lots: ReadonlyArray<Lot>;
  readonly buildings: ReadonlyArray<PlanBuilding>;     // one per built lot
  readonly floors: ReadonlyArray<PlanFloor>;           // build order
  readonly props: ReadonlyArray<PlanProp>;
  readonly totalFloors: number;                        // === floors.length
}
interface Lot { id; x; z; w; d }                       // footprint in cells
interface PlanBuilding {
  id; lotId; archetypeId; height: number /* levels */; color: string; // color: CR6.T3
  landmark: boolean; name: string | null;                // names only on landmarks
  sections: ReadonlyArray<Section>;                      // setbacks, twins, spire
}
interface PlanFloor { building: number; level: number; section: number }
```

Rules:

- **Seed.** `seedFromSession(sessionId)` moves to `lib/city/plan/seed.ts` and
  stays `hashString(sessionId ?? '')` (32 bit). `generateSessionId` is random
  per session: the leading epoch ms differs for every start and the 8 base-36
  characters add about 41 bits of entropy from `Math.random()` (injected,
  §1.4). A collision needs the same millisecond and the same eight characters,
  so two sessions never share a plan in practice. The PRNG for generation is a
  small seeded generator (`mulberry32`) created from the seed in
  `lib/city/plan/rng.ts`; no code calls `Math.random()`.
- **Fixed bounds** (constants in `lib/city/plan/limits.ts`, the single place
  later tasks read):

  | Limit | Value |
  |---|---|
  | Ground | 12 × 10 cells |
  | Lots per plan | **30–48** (`MIN_LOTS`, `MAX_LOTS`; measured, see "Ground plan as built") |
  | Empty lots (parks) | ≤ 10% of lots |
  | Levels per building | 2–16 by archetype; landmarks 16–26 (`MAX_BUILDING_FLOORS` = 32) |
  | Total floors | **200–300** (`MIN_TOTAL_FLOORS`, `MAX_TOTAL_FLOORS`), re-derived in CR6.T2b from 120–180 |
  | Landmarks | 1–3 |
  | Props | lamps ≤ 40, signs ≤ 12, beacons ≤ 4 |

  The generator raises or trims the shortest and tallest non-landmark buildings
  (seeded, one floor at a time) until `totalFloors` is inside the range, so a
  plan always has between 2 and 3 characters per floor (`600 / totalFloors`).
  The tallest building is `32 × 0.35 = 11.2` world units against a 12-unit
  ground, so the camera frame (CR6.T6a) is one constant for every plan.
- **Ground plan as built (CR6.T2a).** `generateCityPlan(seed, options?)`
  (`generate-city-plan.ts`) draws a layout and an offset (`planRoads`), then
  `packLots` scans the land row by row and covers every free cell with a lot:
  the footprint is drawn by weight and, where it does not fit, the largest one
  that does is used (1×1 always fits), so lots and roads tile the 12 × 10 ground
  exactly. Measured over 1,000 seeds with the shipped data, the packing gives
  32–54 lots (means 41–46 per layout), so the plan range is **30–48**, not the
  24–40 first guessed; `packWithinBounds` retries up to 12 times and keeps the
  closest attempt, which stays deterministic. `layouts` and `footprints` can be
  passed as options. With 30–48 lots the first total of 120–180 floors left
  only 2.5–6 per building, too low for the archetype ranges, so CR6.T2b set it
  to **200–300** (2–3 characters per floor).
- **Buildings as built (CR6.T2b).** `placeBuildings` (`plan-buildings.ts`) first
  leaves up to 10% of the lots as parks, picks 1–3 landmark lots (larger lots
  first) and draws an eligible archetype by weight and a height inside its
  range for every other lot. `fitTotalFloors` (`fit-total-floors.ts`) then moves
  regular buildings one level at a time, chosen by the generator, until the
  total is inside 200–300; landmarks keep their height, and when no height can
  move it swaps a building to the lowest- or highest-floor archetype. Landmarks
  get a unique `PREFIX SUFFIX` name (`tower-names.ts`); regular buildings have
  none. `orderFloors` (`build-order.ts`) shuffles the buildings and lists each
  one bottom-up, level by level, all its sections of a level before the next
  level. Props (`plan-props.ts`): lamps on about 30% of the road cells (≤ 40),
  signs on about a third of the buildings (≤ 12), beacons on landmarks first,
  then spires (≤ 4). `generateCityPlan(seed, options)` accepts `archetypes` and
  `towerNames` besides the ground options. Colors and palettes are CR6.T3.
- **Colors as built (CR6.T3).** `chooseStyle` (`assign-colors.ts`) draws a
  palette and an integer hue shift in [−25, 25] from the seed; the palette's
  colors are turned in HSL (`color-math.ts`: lightness and saturation are kept,
  greys are unchanged). `colorBuildings` gives each building a random color not
  used by the buildings already colored that share an edge with its lot (not
  across a road, not at a corner), or the least used among them if all are
  taken. Windows take the palette's `window`, lamps its `lamp`, beacons its
  `beacon`, and a sign wears its building's color. **Minimum luminance (set
  here, CR6.T1 had left it open):** every building, window, lamp, sign and
  beacon color has a WCAG contrast ratio of at least **4.5:1** on the floor
  (`MIN_COLOR_CONTRAST`); a test checks every palette color at every shift from
  −25° to +25°. The environment (`environment-colors.ts`: floor `#000000`, grid,
  rain and HUD `#7dfba0`) is constant. The plan gains `paletteId`, `hueShift`,
  `PlanBuilding.color`/`windowColor` and `PlanProp.color`.
- **Variation sets (data, Open/Closed).** Adding one is an array entry:
  - *Road layouts* (4, `road-layouts.ts`): `grid` (one avenue, two streets),
    `crossroads`, `comb` (one avenue with three side streets), `ring` (a loop
    road around a core); the whole layout moves rigidly by an offset of ±1 cell
    on each axis and is clipped to the ground, so it stays connected.
  - *Lot footprints* (`LOT_FOOTPRINTS`): 1×1 (10%), 2×1 and 1×2 (30% each),
    2×2 (30%), packed over the land cells.
  - *Archetypes* (6, `building-archetypes.ts`; levels): `tower` (one box,
    5–14), `slab` (wide lots only, 2–6), `stepped` (three setbacks, 8–16),
    `twin` (two towers on a lot of area ≥ 2, 4–10, two floors per level),
    `spire` (box plus a 3-level needle, 8–14), `lowBlock` (2–4). Landmarks are
    drawn from `tower`, `stepped` and `spire` with their own range (16–26).
    Each entry holds its weight, ranges, minimum lot area and a pure section
    builder.
  - *Palettes* (6, `city-palettes.ts`): Neon City, Sunset Strip, Arctic Dawn,
    Toxic Grid, Synthwave, Amber Terminal; each with six distinct neon colors and
    the accents of windows, lamps and beacons. See "Colors as built".
  - *Props*: lamps along roads, signs on about a third of the buildings,
    beacons on landmarks and spires; placed with the same seeded generator.
  - *Names*: prefix × suffix word lists in `lib/city/plan/names.ts`
    (e.g. `NEO` `QUANTA`, `HELIX` `TOWER`), only for landmarks (≤ 3 labels).
- **Build order.** Buildings are shuffled with the generator; each building
  lists its floors bottom-up; `floors` is the concatenation. Floor `k` of the
  plan is the `k`-th floor to appear. Landmarks are not forced last: a city
  grows from several places at once.

## 4. Visible floors and the damaged top floor

```
exact   = built / total × plan.totalFloors        // built in [0, total]
complete = floor(exact)
partial  = exact − complete                        // 0 ≤ partial < 1
```

- Nothing at `built = 0`; every floor complete at `built = total`; monotonic;
  invalid input (non-finite, `total ≤ 0`) → nothing. Lowering `built` removes
  the highest build-order floor first.
- **The partial floor.** It is the floor at index `complete` in build order.
  - While the city grows (no characters lost) it is **under construction**:
    drawn as a dim wireframe with its edges only, scaled in height by `partial`.
  - Once the session has lost characters it is **damaged**: cracked, flickering
    red edges. "Lost" is `lostCharacters > 0`, with
    `lostCharacters = max(0, focusCharacters − built)` and
    `focusCharacters = min(total, floor(focusedMs × total / durationMs))`.
    Both come from the persisted `timer` accumulators, so the popup needs no new
    state and the damage survives a restart.
  - A drop of a single character moves `exact` by `floors / 600` (≈ 0.33–0.5
    floor), so the partial floor or the visible count changes every time: the
    "every lost character is visible" rule holds without a separate rule.
- **Amends the CR6.T4 card.** The card said the partly paid floor is *always*
  damaged. That would make every floor flash red while the city grows. The
  signature becomes `visibleFloors(plan, built, total, lostCharacters)` returning
  `{ complete, partialFraction, damaged }`; the card is updated in the roadmap.
- **As built (CR6.T4).** `visibleFloors(plan, built, total, lost)` and
  `calculateLostCharacters(focusedMs, durationMs, built, total)`
  (`visible-floors.ts`) implement the formula above; the focus part reuses the
  new `calculateFocusCharacters` exported by `lib/score/calculate-built-characters.ts`
  (no behavior change there). **Scene data** is split in two so growth does not
  rebuild arrays: `createScenePlan(plan)` (`scene-data.ts`) builds, once per
  plan, typed arrays for *every* floor in build order (16 floats per matrix, 3
  per body and window color, 6 per edge segment, 12 segments per floor, plus the
  landmark labels with the build-order index where their building is complete);
  `createSceneFrame(scene, plan, visible)` is the cheap per-update result:
  `instanceCount` (complete floors plus the partial one), `edgeSegmentCount`,
  the `partial` floor with its own scaled matrix and edges and its `damaged`
  flag, and the visible label indexes. The renderer uploads the static arrays
  once and only changes the instance count and the partial slot. World units:
  one floor is `FLOOR_HEIGHT` = 0.35 tall (body 94% of it), the city is centered
  on the origin, a partly paid floor is at least 15% of a floor tall.
  `summarizePlan` (`plan-summary.ts`) returns buildings standing, floors built
  of total, the tallest building (levels and landmark name) and a milestone
  0–10 that moves every 10% of the floors; the component words it.

## 5. Option A — the malus inside `builtCharacters`

Decision (2026-11-11): the M4.T1 escalation enters the score.

```ts
distractionCharacters(distractedMs, durationMs, total) =
  malusForDistractionTicks(floor(distractedMs × total / durationMs))

built = max(0, floor(focusCharacters − distractionCharacters))
```

- **Same clock.** `tickMs = duration / total`, so
  `floor(distractedMs / tickMs) = floor(distractedMs × total / durationMs)`:
  the number of distraction ticks is the same quantity the score already uses.
  Stage 1 (1 per tick) equals today's linear penalty, so only stays beyond five
  ticks get harsher, exactly as M4.T1 intended.
- **Which distraction time.** All `timer.distractedMs` (the cumulative total of
  the session). The wiring's "stretch" is already one per session, so
  cumulative equals the stretch except for the seconds between opening the blocked
  tab and answering "Open anyway". The score already counts those seconds today
  (the tracker books the whole tab time as distraction), only the city forgave them.
  Keeping a "proceed" baseline would need a new persisted accumulator and a
  migration step for no real gain, so it is dropped (decision for the developer
  to confirm; the alternative is one extra `timer` field).
- **The immediate character at "Open anyway" is dropped.** `pump` removed one
  extra character at the moment of the choice (`expected = 1 + malus(n)`). The
  score is a function of accumulated time, so it has no event term; the overlay
  already shows its own feedback.
- **`MALUS_APPLIED`** keeps its type. `createMalusWiring` stays (it still knows
  the `domain` of the last "Open anyway") but no longer touches the city: when
  an accounting step lowers `builtCharacters` it sends
  `{ domain, charactersRemoved: previous − next }` once per positive drop. No
  layers, no `countOccupied`. Nothing consumes it today, so the message is
  informational.
- **Module split.** `MALUS_ESCALATION_SCHEDULE` and `malusForDistractionTicks`
  move to `lib/score/malus-escalation.ts` (CR6.T5b); `apply-malus.ts` has
  nothing left and is deleted in CR6.T9a.
- **As built (CR6.T5b).** `lib/score/malus-escalation.ts` holds `MALUS_ESCALATION_SCHEDULE` and `malusForDistractionTicks` (moved out of `apply-malus.ts`, whose ASCII `applyMalus` stays until CR6.T9a); `calculateBuiltCharacters` charges `malusForDistractionTicks(floor(distractedMs × total / durationMs))`. `advanceProgress` no longer returns `targetTicks` nor takes `tickMs`: the background's progress tick records the accumulators and `builtCharacters` and never grows or erases layers. `createMalusWiring` no longer takes the distraction tracker: it subscribes to the store and, once the user chose "Open anyway", sends `MALUS_APPLIED { domain, charactersRemoved }` when an accounting step that added distraction time lowers `builtCharacters` (the drop); a drop with no new distraction time (a reset) and a new session send nothing. Session-completion tests whose expected tiers moved are named for the escalation.
- **Effect on the CR3 bands.** Escalation makes stays beyond ~1% of the session
  noticeably harsher. `d` = fraction of the session spent on blocked sites, the
  rest focused (600 characters):

  | `d` | distraction ticks | old penalty | new penalty | built (new) | old → new tier |
  |---|---|---|---|---|---|
  | 1% | 6 | 6 | 7 | 587 (97.8%) | great → great |
  | 5% | 30 | 30 | 74 | 496 (82.7%) | great → great |
  | 10% | 60 | 60 | 164 | 376 (62.7%) | great → **good** |
  | 20% | 120 | 120 | 344 | 136 (22.7%) | good → **bad** |
  | 33% | 200 | 200 | 584 | 0 | good → **bad** |

  Example: 30-minute session, 60 s on a blocked site (20 ticks): the score and
  the city both lose 44 characters (5 + 12 + 27), not 20. Five minutes on a
  blocked site in the same session (100 ticks) costs 284 characters, 47% of the
  city. Because ticks scale with the session, the same *fraction* of time costs
  the same in every preset.
- **Tests that change** (CR6.T5b): `calculate-built-characters`,
  `session-progress`, the score-tier and population tests whose expected values
  depended on a long distraction. Test names say the escalation is why.

## 6. Persistence v3 → v4

- **Dropped from `city`:** `layers`, `buildings`, `themeId`. **Kept:**
  `sessionId`. The state is `{ sessionId: string | null }`; the plan is a
  memoized selector `selectCityPlan(sessionId)`, never persisted.
- `migrateCity(raw)` (`lib/city/migrate-city.ts`) returns a `Result`: from a
  v3 snapshot it keeps `city.sessionId` when it is a string, drops the rest,
  and rejects malformed data (a non-object `city`) with an error, falling back
  to `{ sessionId: null }` at the caller. v2 fixtures chain through the existing
  v2 → v3 step first.
- **A session in progress at the upgrade** keeps `timer`, `score` and
  `city.sessionId`, so its score is unchanged and its plan is generated from the
  session id on the next read. Its first view is therefore a new-looking city
  with the same completion percentage. Old ASCII layers are not converted.
- The popup store stays read-only; only the background writes `city.sessionId`.
- **As built (CR6.T5a).** `migrateCity` and `sanitizeSessionId` live in
  `lib/city/migrate-city.ts`; a rejected city is logged (`city migration
  rejected`, version and key only) and falls back to `{ sessionId: null }`
  while the rest of the snapshot migrates normally. `partialize` writes
  `city: { sessionId }` and `merge` applies only the sanitized session id.
  `selectCityPlan(state)` and `selectVisibleFloors(state)` (`store/city.selectors.ts`)
  remember one entry each (plan by session id, floors by plan, built and lost
  characters), so the plan is generated once per session and a component
  selecting the floors re-renders only when the city changes. **Transitional:**
  the ASCII `layers`, `buildings` and `themeId` stay in `CityState`, in memory
  only and no longer persisted, so the background's growth and malus (CR6.T5b)
  and their tests keep working until CR6.T9a deletes them. The popup rehydrates
  from storage, so its old ASCII City view is blank from this task until
  CR6.T8a draws the plan; a worker restart also loses the redrawn ASCII
  characters.

## 7. Rendering decisions

- **three.js**: exact-pinned (no caret) to the latest stable at CR6.T6a. It is
  `0.187.0` at the time of writing; the task re-checks. Imports are
  `three` and `three/addons/...` (`EffectComposer`, `RenderPass`,
  `UnrealBloomPass`, `ShaderPass`, `OutputPass`; no `OrbitControls` unless the
  camera interaction needs it). **Approved exception** to the minimal-dependency
  rule (§1.4), recorded here. No other new dependency.
- **As built (CR6.T6a).** `three` and `@types/three` 0.187.0 are installed (exact). `lib/city/render-scheduler.ts` is the pure decision: a frame is drawn for a pending `floors`, `camera` or `resize` change or a due ambient frame (never more than 30 fps, none under reduced motion); a hidden view draws nothing and keeps its changes pending; `needsLoop` is false when idle or hidden, so no frame callback is even requested. `lib/city/camera-framing.ts` holds the fixed isometric framing (`VIEW_SIZE` 20 world units, `CAMERA_HOME`, `CAMERA_TARGET`) and the orbit limits (a quarter turn either side of the home azimuth, polar 0.5–1.35 rad, zoom 0.8–1.8, no pan). `components/city/three/renderer-context.ts` creates the `WebGLRenderer` (`antialias: false`, `powerPreference: 'low-power'`, `preserveDrawingBuffer: false`, pixel ratio capped at `MAX_PIXEL_RATIO` 1.5), the orthographic camera, the scene and `OrbitControls` (no pan, no damping); `city-renderer.ts` is the lifecycle: `createCityRenderer(options)` returns a `Result` (an error when WebGL cannot start), and the renderer offers `resize`, `invalidate`, `setVisible`, `setReducedMotion`, `registerDisposable` (for CR6.T6b/T7 render targets and passes), a `renderCount` for the e2e probe and an idempotent `dispose()` that cancels the frame, removes its listeners, disposes the scene's geometries, materials and textures, the renderer and forces context loss. `webglcontextlost` is reported through `onContextLost` and stops drawing. It also listens to `visibilitychange`, so a hidden document stops it even if the view above forgets to say so. The scene itself is empty here; CR6.T6b adds the meshes.
- **Loading.** `CityView3D` is `React.lazy` + dynamic `import()`, so WXT/Vite
  emits a separate chunk. The Timer tab never loads it. CSP: three.js needs no
  `unsafe-eval`; CR6.T12 confirms it in the built extension for both browsers.
- **Module split** under `components/city/three/`:
  `city-renderer.ts` (lifecycle: create, resize, render, dispose,
  `captureFrame`), `build-meshes.ts` (instanced floors and window bands, edge
  line mesh, ground/grid), `post-processing.ts` (bloom at half resolution, CRT
  `ShaderPass`), `ambient-layer.ts` (rain, cars, flicker, beacons),
  `webgl-support.ts`; React: `CityView3D.tsx`, `CityFallback.tsx`,
  `CityStage.tsx`. Pure scheduling in `lib/city/render-scheduler.ts`.
- **Render on demand.** The scheduler decides, from a state snapshot (dirty flag,
  visible, reduced motion, last ambient time), whether to draw; it never reads
  a clock itself (§1.4, injected `now`).
- **Fallback.** `plan-skyline.ts` renders the plan as ASCII columns (height per
  building column, characters per floor) at the fixed 60 × 20 size the old tab
  used; shown when `webgl-support` says no, or on `webglcontextlost`. The text
  summary (`plan-summary.ts`: buildings, floors built of total, tallest
  building) is shared by both views and updated at milestones (every 10% of
  floors), not per floor.
- **Export** (CR6.T10): `captureFrame(width, height)` renders one frame at the
  chosen size to the canvas and calls `toBlob` in the same task, so
  `preserveDrawingBuffer` stays off. The result goes through the existing
  `Result`-based export boundary and `rasterize-image.ts` (kept for the ASCII
  fallback). The export button stays visible only when `completed`.
- **Test strategy.** happy-dom has no WebGL, so: (1) everything that decides
  what is drawn is pure and in `lib/` (plan, floors, scene data, scheduler,
  summary, skyline) with unit tests; (2) component tests mock `city-renderer`
  and assert lifecycle (mount, resize, dispose, fallback switch); (3) real
  rendering is covered in Playwright (`tests/e2e/city-3d.spec.ts`) with a
  `data-render-count` attribute on the canvas host that the e2e reads.
